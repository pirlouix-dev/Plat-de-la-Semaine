# Development guide

## Layout

- `frontend/` — React app. Run npm commands from this directory.
- `backend/` — ASP.NET Core API. Run dotnet commands from this directory.
- `openapi.yml` — generated at the repository root, consumed by the frontend.
- `docs/` — repository-level documentation.

## Branching

Never commit or push directly on `develop` or `main`. If you find yourself on
either branch, create a new branch from `origin/develop` first:

```sh
git fetch origin
git switch -c <branch> origin/develop
```

Open pull requests against `develop`. A pull request may change the frontend,
the backend, or both.

## API contract workflow

`openapi.yml` is generated by `backend/generate-openapi.sh` and committed at the
repository root. The frontend generates `frontend/src/schema.d.ts` from it.

Whenever you change the API:

1. Run `./generate-openapi.sh` in `backend/`.
2. Run `npm run gen:api-types` in `frontend/`.
3. Commit `openapi.yml` and `frontend/src/schema.d.ts` with the change.

Do not hand-edit either generated file.

### Error contract

The backend returns a stable machine-readable `code` in every error envelope.
The frontend is the only place that maps a `code` to localised user-facing copy
(`getApiErrorMessage` in `frontend/src/services/api.ts`). The backend `message`
is an English diagnostic and must never be rendered in the UI.

Frontend and backend are released together. Do not add client-side
compatibility mappings for error codes the backend no longer sends; remove the
old mapping and the backend code in the same release.

## Testing

- Frontend tests live in `frontend/src/__tests__/`; `frontend/src/test-setup.ts`
  configures jsdom, `fake-indexeddb`, and Testing Library.
- Backend tests live in `backend/tests/`.
- When touching sync/conflict logic, cover both the success path and the 409
  follow-up (pull, resolve, retry) in `syncService.test.ts`.

Run both suites before opening a pull request:

```sh
cd frontend && npm test
cd backend && dotnet test
```

## Dependencies

`.github/dependabot.yml` opens weekly version-update pull requests against
`develop` for npm (`frontend/`), NuGet (`backend/` and its test project) and the
workflow actions. Minor and patch bumps are grouped; major bumps arrive as
individual pull requests and are never auto-merged.

An `openapi-typescript` or `typescript` bump can change the generated types:
run `npm run gen:api-types` in `frontend/` and confirm `src/schema.d.ts` is
unchanged. A `Microsoft.OpenApi` bump is part of the API contract workflow
above — regenerate `openapi.yml` in the same pull request.

Majors arrive as individual pull requests and are merged by hand. Two cases are
blocked for now and their pull requests should be closed rather than merged:

- `typescript` majors, until `typescript-eslint` widens its peer range (it
  currently allows `<6.1.0`). This one is ignored in the config so it is not
  reopened every week.
- `Microsoft.AspNetCore.*` and `Microsoft.OpenApi` majors, which only move with
  a `net11.0` target. They are listed under `ignore` too, but Dependabot's NuGet
  support does not honour `update-types` ignores yet
  (`dependabot-core#11398`), so the pull requests still show up.

## Python tooling

Any Python library may be used for one-off work (image processing, scripts),
provided it is installed into the `venv` directory at the repository root:

```sh
python3 -m venv venv
venv/bin/pip install <package>
venv/bin/python script.py
```

`venv/` is gitignored and never committed.

## Code comments

Comment only what the code cannot show on its own: non-obvious constraints, why
a surprising choice was made, or a workaround with its context. Do not narrate
what a statement does — a comment restating the next line is noise. Prefer clear
naming over explaining code.

While you are already editing a file, delete comments that are plainly obvious
or redundant — do not leave them for a separate cleanup pass.

## GitHub CLI

`gh` is installed and authenticated. Use it to inspect issues and manage pull
requests, for example:

```sh
gh issue view 93
gh pr list
gh pr create --base develop --head <branch>
```

The remotes are HTTPS URLs and authenticate through `gh`'s credential helper:

```sh
gh auth setup-git   # once per machine
git push
```

Plain `git fetch`, `git pull` and `git push` work as-is.
